# Connect to a Database review

Observed situation: the tutorial preserves logical database creation, writer-independent peer connections, a first EDN transaction, six-coordinate reports, and retained-receipt retries. It supplies one transaction source and describes automatic timestamp attribution correctly. The Rust example uses a native `EntityRef::Ident`, while CLI `--source` constructs deferred `EntityRef::Edn`; the page promises that running these examples with the same key replays one receipt.

Cause and bounded problem: `src/encoding/mod.rs::encode_entity_ref` intentionally encodes native Ident with tag 1 and deferred EDN with tag 6. `canonical_submission_request` includes those bytes before authoritative source resolution. Therefore those two documented complete requests differ, despite resolving to the same entity. Make the two examples express one identical EDN request without changing request identity, resolution, storage, or native reference APIs.

Approaches and tradeoffs: changing canonical identity to equate resolved/native and EDN references would entangle receipt lookup with schema-dependent resolution and affect unrelated callers; weakening the retry promise would remove useful cross-interface behavior; constructing the Rust source with `EntityRef::from_edn` reuses the existing schema-independent mechanism and keeps retry reasoning local to complete input data. Select the latter. This separates source intent from ordinary resolution and preserves composability across CLI and Rust transport boundaries.

Acceptance: reconstruct both complete requests from the page's literal Rust and CLI examples and require equal canonical submission digests; confirm a different source intent changes identity. Existing live evidence supports unchanged transport, automatic timestamp, reports, writer-independent reads and retained receipt behavior; inspect rather than rerun the broad workflow.
