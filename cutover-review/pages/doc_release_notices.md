# Release notices review

Observed situation: `docs-2/00_start_here/06_release_notices.md` correctly identifies an unpublished, unlicensed `0.1.0` development package and distinguishes installation, native-object compatibility, backup verification, recovery, and completed excision. It warns against assuming package-version compatibility, but does not yet identify the source cutover's concrete input and fact changes.

Cause and bounded problem: source is now an independent, mandatory coordinate of every datom and transaction request. Readers of this compatibility page need to recognize that boundary without a new migration mechanism or a duplicated API reference. Review every existing notice against the implementation and existing acceptance evidence; add only the compatibility details needed to connect the page to NORTHSTAR and the timestamp reference.

Approaches and tradeoffs: retaining only the generic earlier-format warning leaves the reason for this cutover implicit. Enumerating every codec constant and operation signature here duplicates independently maintained references. A short paragraph naming the six-field datom, one request source, automatic timestamp attribution, six index orders, and fresh-storage requirement describes the boundary while linking the authoritative details.

Selected implementation: preserve the page's existing section structure and truthful development status. Add a short source-model paragraph under earlier-development compatibility. Preserve ordinary entity-reference resolution and original transaction-form arities through the linked reference. No adapters, defaults, upgrade converter, release declaration, or production-resource changes.

Design criteria: installation format and logical database codecs remain independent checks; backup copying and semantic verification remain independent operations. Reuse their existing mechanisms. A source contribution remains ordinary data, composable with schema and history, rather than a separate migration subsystem. This keeps compatibility reasoning local and allows format changes without coupling them to the package version.

Acceptance checks: inspect package metadata, storage installation and connection gates, current native decoders, request/source/timestamp invariants, backup verify/restore paths, canonical-log consolidation and excision completion, and the two query/entity-boundary limitations. Reuse the integrated and live workflow logs for unchanged behavior, then check the assigned page's links and diff. Coordinate any implementation discrepancy with root before editing code.
