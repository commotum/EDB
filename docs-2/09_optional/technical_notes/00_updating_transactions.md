# Comparison with Updating Transactions

Some database systems compose transactions from a series of updates, where each update changes the state of the database. Depending on the degree of isolation provided, transactions might also see interleaved updates from other transactions, e.g. *a′* might not even equal *b* in:

```text
BEGIN TRANSACTION
UPDATE ... ;; db state a -> db state a′
UPDATE ... ;; db state b -> db state b′
UPDATE ... ;; db state c -> db state c′
COMMIT
```

This is illustrative pseudocode for an updating transaction, not EDB transaction syntax.

EDB transaction execution is not defined as a series of updates. This section highlights the differences, which may be helpful to people accustomed to working with updating transactions.

An EDB transaction [is defined as the addition of a set of datoms](../../04_transactions/04_transaction_data.md) to the previous (db-before) value of a database. In particular, an EDB transaction is not defined as a batch of smaller updates. Assertions and retractions are not read/modify/write operations, nor are they functions of `db -> db`; they are just information, and the transaction's operation is to append the assessed information, as a set, to db-before. Ordinary transaction application does not mutate the captured db-before value. Current-state reads omit retracted facts, while history exposes retained assertions and retractions. Retention policies such as [noHistory](../../03_schema/02_schema_reference.md#dbnohistory) and [excision](../../08_operations/00_deployment.md#excision) mean that retaining all historical information forever is not an unconditional promise.

No rules about the order of read/modify/write updates within a transaction can be violated by EDB, as no such updates are provided. The assessor resolves identities, eliminates redundant facts, derives necessary retractions and checks the complete proposed successor. For example, asserting two different values for one cardinality-one attribute fails; the last form in the input does not win.

EDB [transaction functions](../../04_transactions/07_transaction_functions.md) are functions of `db-before × args -> tx-data`. They do not update anything. In particular, EDB does not use the data returned from transaction functions to produce interim database values. All calls, including calls generated by other functions, see the same db-before. Native Rust callbacks must honor this pure-function contract; Rust itself does not prevent external effects.

Compared to systems that compose transactions from updates, EDB's transactions enable a set of guarantees that facilitate reasoning about programs:

- Database values incorporate transactions only at complete transaction boundaries; temporal and filtered views can select a subset of their facts.
- Every fact (datom) in a database is associated with a complete transaction.
- Every datom belongs to the database's logical transaction order. Its `tx` field identifies its transaction; Rust's `tx_to_t(datom.tx)?` recovers logical `t`. A database value's `basis_t()` identifies its captured basis. See [Datoms](../../07_peer_api/types/05_datom.md).

An incremental-update interface alone does not provide these immutable database values and per-fact transaction references. Other database systems may provide atomic commits and isolation guarantees of their own; the distinction here is EDB's model of complete database values and declarative transaction data.

Check [Integrity and Composition](../../04_transactions/05_transaction_model.md#integrity-and-composition) for how to compose transaction data that enforces domain invariants.
