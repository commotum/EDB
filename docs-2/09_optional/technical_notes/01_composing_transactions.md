# Composing Transactions, by Example

## Example 1

Imagine that you are building a database that records the following two actions that a person might perform:

1. A person can purchase a house, but only while living.
2. A person can get married, but only while living.

In addition, your stakeholder is considering an additional requirement that these records include audit data that must be generated by the system. To record these actions, you might use EDB’s [transactions](../../04_transactions/05_transaction_model.md), [transaction functions](../../04_transactions/07_transaction_functions.md), and [entity predicates](../../03_schema/02_schema_reference.md#entity-predicates), which have the following semantics:

1. A *transaction* takes the start-of-transaction database value (`db-before`) and *transaction data*, and produces a new database value (`db-after`). Transaction data can include both primitives (requests for assert and retract) and data requesting *transaction functions*.
2. EDB calls transaction functions with `db-before` plus user arguments, returning more transaction data, recursively until all that remains are primitive operations. The union of these operations is then assessed as one atomic operation against `db-before`, producing `db-after`. The resulting information must satisfy EDB’s built-in constraints; union does not make conflicting assertions valid.
3. Transaction data can also include special assertions (`:db/ensure`) naming entity specs. The specs name entity predicates through `:db.entity/preds`. These predicates are invoked against `db-after` and an entity ID, and composed via logical *and*, i.e. all entity predicates must return literal `true`, or the transaction aborts. Specs must already exist in `db-before`, and checks run only when explicitly ensured.

There are many ways to record the two actions. Here are some examples:

1. Use two transaction functions, one for each action. If the person is living as of `db-before`, the transaction function returns data to record the marriage/purchase plus the system audit data. If the person is dead, a native transaction function returns a `SemanticError` to abort the transaction; a stored program can reject with `Require` or `RequireAnomaly`.
2. Transact the data for each action along with ensures for two entity predicates, one for each action. These can check `db-after` to verify that a person is living, and return false to abort the transaction if the person is dead. Entity predicates receive `db-after`, not a separate `db-before` argument; use a transaction function when the rule is specifically about the starting state.
3. Use a combination of transaction functions and entity predicates.

If you think about the difference between these three approaches, you may decide the original requirements were imprecise, e.g.:

1. Can a person get married and purchase a house in a single transaction?
2. Can a person’s death be recorded in the same transaction as a marriage or house purchase?

Comparing the three approaches, assuming that each action’s data can coexist under the schema:

|  | Only tx functions | Only entity predicates | Tx functions and entity predicates |
| --- | --- | --- | --- |
| Can a person get married and buy a house in the same transaction? | Yes with the functions above: both read the same living person in `db-before`, and their data is composed by set union | Can allow or disallow via entity predicates | Can allow or disallow via entity predicates |
| Can a person’s death be recorded in the same transaction as a marriage or house purchase? | Yes with the functions above: recording death does not change the `db-before` seen by either function | Can allow or disallow via entity predicates | Can allow or disallow via entity predicates |
| Generate the system audit data | Transaction functions can generate the audit data | Entity predicates can at best reject a transaction missing the audit data | Transaction functions can generate the audit data |

Before committing to one of these approaches, you might want to more precisely nail down the domain requirements. But instead of doing that, let’s make things more difficult by adding a meta-requirement: your system is evolving quickly. These two actions are the first of many, and there will be new ones coming every week. Moreover, the stakeholders sometimes realize that they got the rules for actions wrong, e.g. they initially prohibited users from taking two actions in the same transaction and later decided that multi-action transactions are ok.

Function composition to the rescue. Transaction functions and entity predicates are top-level entry points between transactions and your code. Each can be composed of smaller functions combined in different ways. Continuing the example, you plan the following Rust helper functions:

1. `action_types` takes a database and a transaction entity ID, and returns a list of keywords naming the actions recorded in that transaction, e.g. `:bought-house` or `:got-married`. Record those action types as application transaction metadata so that this function can read them.
2. `add_audit_data` takes `db-before` and transaction data, uses an action type to determine the type of action, and then dispatches to a helper to generate action-specific audit data.
3. `is_alive` takes a database and entity ID and returns true if the entity is a person currently living.

These are application helpers, not built-in EDB functions. Note that these should all be pure functions, free of side effects. There is no implicit database being mutated in the background—it is up to you to flow all relevant information via function arguments and returns. Rust’s callback types do not enforce purity. In particular, deriving audit data should use the supplied database and arguments, not external I/O or changing process state. Here are a few examples showing how these functions can be composed to meet domain requirements:

If the stakeholder decides that audit data is required and that users can get married / buy a house / die all in the same transaction, you can implement `get_married` and `buy_house` as transaction functions that:

1. Check `is_alive`, aborting if the person is not alive in `db-before`.
2. Call `add_audit_data` based on the single action type implied by the transaction function’s name, returning the action data and audit data together.

If instead the stakeholder decides that audit data is not needed and that users can perform only one action in a transaction, then you can invoke two entity predicates:

1. `is_alive` (which will now act against `db-after`), ensured on the person.
2. `one_action_only`, ensured on the transaction entity, calls `action_types` and returns false if it returns more than one.

The second predicate requires the action-type metadata even when the additional audit data is not needed. The predicates must be named by entity specs, and each transaction must ensure the relevant specs. In Rust transaction forms, `EntityRef::Tx` names the current transaction entity; in EDN, use `"edb.tx"`. See [transaction data](../../04_transactions/04_transaction_data.md#reified-transactions).

Other variations on the initial requirements can be composed similarly. To deploy compiled Rust transaction functions and entity predicates, register them with a `NativeRegistry` and supply that registry to the host. See [native application computation](../../07_peer_api/02_native_computation.md).

## Example 2

Next let’s consider a lower-stakes example, the grant approval process. Here are the requirements:

1. A grant can be approved, but only if it has not yet been approved or denied.
2. A grant can be denied, but only if it has not yet been approved or denied.

This example is somewhat similar to the person example, except now the two transitions are definitively exclusive. This rules out relying only on two independent transaction functions that check the starting state and emit otherwise compatible data. Transaction function outputs are composed via *union*, which is inclusive, not exclusive. Both functions would see the same undecided grant in `db-before`.

The logic of entity predicates is a good fit here, and there are some different ways you might compose them. For example, if approval and denial are separate attributes, ensure a predicate that rejects a `db-after` containing both. Keep the starting-state check in the transaction functions to prevent a later decision from replacing an earlier one.

Alternatively, a single cardinality-one `:grant/status` attribute can make simultaneous assertions of distinct approved and denied values conflict under EDB’s built-in rules. A [`:db/cas`](../../04_transactions/07_transaction_functions.md#dbcas) from the pending status to the desired decision checks the starting state. Prefer built-in constraints where they express the requirement; use entity predicates for invariants that need to inspect the complete proposed state.
